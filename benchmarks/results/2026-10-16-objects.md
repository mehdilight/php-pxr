# Object and heap optimization — 2026-10-16

The remaining object hotspot is addressed with inline property storage, allocation
effect analysis and a growing heap pointer index. The existing 2,000,000-object
workload fell from 292.000 ms to 100.490 ms (**2.91× faster** than the previous
PXR runtime). Reusing one object for 2,000,000 method calls fell from 75.001 ms to
7.392 ms (**10.15× faster**). Keeping 100,000 objects alive and reading them fell
from 242.761 ms to 12.121 ms (**20.03× faster**).

An improvement above 1 means PXR became faster. All twelve cases finish faster
than this installed PHP CLI, including the three object cases. This is an
end-to-end microbenchmark result, not a claim that every PXR program is faster.
Other small differences are not an optimization claim; the string-key case, for
example, measured about 0.24 ms slower than the baseline in this run.

## Method and reproduction

* Apple M3 Max, 36 GiB, macOS 15.8.1 arm64; Apple clang 17.0.0.
* PHP 8.4.25 CLI with installed Herd settings, CLI OPcache off and JIT disabled.
  PXR release compiler, programs built with `--opt 3`.
* Two warmups and nine measured runs per runtime. Execution order alternates
  PXR/PHP; timings include startup and teardown and exclude compilation.
* All twelve source hashes and outputs agree between reports. The two new object
  workloads also run under the saved baseline compiler. No test suites ran
  during these measurement runs.
* The baseline compiler is revision `784bf88`. The after report uses the modified
  compiler/runtime. Raw reports record binary SHA-256 values; their git revision
  is the workspace HEAD before this optimization commit.

```sh
# Save the baseline compiler before rebuilding the modified compiler/runtime.
cp target/release/pxr /tmp/pxr-before-object-optimization
cargo build --release -p pxr
python3 benchmarks/bench.py --pxr /tmp/pxr-before-object-optimization \
  --repeat 9 --warmup 2 --json /tmp/objects-before.json
python3 benchmarks/bench.py --repeat 9 --warmup 2 \
  --json /tmp/objects-after.json
```

## Profiling and implementation

A one-second macOS `sample` capture of an enlarged object loop showed GC polling,
root publication, thread-local access and allocation/free operations among its
hot stacks. Each native object formerly required three tracked allocations.
A second profile of an enlarged retained-object case showed collection dominating;
the fixed 4,096-bucket heap pointer index developed long chains as the heap grew.
These captures guided the changes; the tables above use independent unprofiled
runs of the committed benchmark sources.

* One allocation now holds the object header and zeroed property tags/payloads.
  The stable header/getter/setter ABI remains unchanged, and zero-property objects
  keep null storage pointers. GC traces properties through their owning object.
* Allocation/collection effects propagate through the whole call graph, including
  recursive functions, constructors and virtual wrappers. Pointer parameters or
  returns alone no longer force a GC frame. Unknown calls remain effectful;
  callbacks, mixed operations and explicit collection keep their roots.
* Allocating operations poll before running, and paths that allocated retain an
  exit poll with live return values rooted. Nonallocating getters, setters, leaf
  methods and branch/loop edges no longer add redundant polls. HTTP printing
  remains allocation-capable because it can grow its output buffer.
* Each thread's heap pointer index mixes aligned addresses, grows at 75% load
  and shrinks after collection below one-eighth occupancy. Resizing preserves
  allocation addresses and exact-pointer lookup never reads before static literals.
  Bucket metadata uses separate system allocations and is excluded from managed
  payload statistics; it is freed at shutdown. Failed optional shrinking leaves
  the existing index intact.

## Correctness and completion

Native tests cover one-allocation objects, zero/large property sets, alignment,
zero initialization, checked size overflow, nested string/array/mixed/object
payloads, cycles, index growth/removal/shrink and literal-pointer rejection.
Compiler tests cover pointer-returning leaf helpers, recursive collection effects,
unknown callbacks and polling decisions. Source tests exercise returned property
values across collection, allocating constructors, transitive callbacks, shared
aliases and cycles under normal and forced GC at O0/O3.

Validation: 276 workspace tests and 71 ASan/UBSan checks passed, plus the
native ThreadSanitizer suite and four worker source tests under ThreadSanitizer.
The release build, checks for every example and running every example also passed.

This closes the current post-M7 optimization pass: array lookup/append,
copy-on-write arrays, local string accumulation, and object allocation/method/heap
costs all have implementations, regression coverage and saved measurements.
The [array-index report](2026-10-16-array-index.md),
[copy-on-write report](2026-10-16-array-cow.md),
[string append report](2026-10-16-string-append.md) and
[original M7 comparison](2026-10-16-m7.md) retain the earlier evidence.
Further performance work can follow future application profiles. Mixed string
accumulators and property/array-element string targets still use ordinary
concatenation; no unsupported language feature is silently enabled by this pass.
The next feature milestone remains M8, whose C interoperability syntax is a draft.
