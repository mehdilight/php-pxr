# M7 benchmark comparison — 2026-10-16

PXR is faster on these scalar CPU benchmarks and slower on the array, string
and object workloads below. These results do not establish a general application
speedup. In particular, PHP startup dominates several small workloads.

| Workload | PXR median | PHP median | PXR relative to PHP |
| --- | ---: | ---: | --- |
| Startup / print | 2.324 ms | 28.323 ms | 12.19× faster |
| Recursive fib(30) | 4.211 ms | 86.670 ms | 20.58× faster |
| Integer loop (5M) | 2.117 ms | 80.486 ms | 38.03× faster |
| Array append + reads (10k) | 83.585 ms | 28.370 ms | 2.95× slower |
| Array copies (100k × 1k items) | 255.348 ms | 29.761 ms | 8.58× slower |
| String append (50k) | 186.140 ms | 29.697 ms | 6.27× slower |
| Objects + methods (2M) | 284.242 ms | 188.742 ms | 1.51× slower |

## Environment and method

* Apple M3 Max, 36 GiB RAM, macOS 15.8.1 (arm64).
* PXR release compiler from `44471ab4a816280e7f9c551ecdda9e615677cd9b`, native
  programs compiled with `--opt 3`; Apple clang 17.0.0. The working tree contained
  the new benchmark programs/harness and draft documentation, with no compiler
  or runtime changes. The raw report records the compiler binary SHA-256.
* Installed PHP 8.4.25 CLI from Laravel Herd, with its ordinary scanned ini file.
  `opcache.enable_cli=0`, `opcache.jit=disable`. This is not a PHP JIT comparison.
* Two untimed warmups per runtime, then nine measured runs. Alternating execution
  order each round; comparisons use the median. Raw samples also retain best/max.
* Every execution uses the identical PHP source and checks byte-for-byte matching
  stdout. Nonzero exits, stderr or mismatched output fail the benchmark.
* Wall times include process creation, runtime startup, program execution and
  teardown. Compilation is recorded separately and excluded from the table.
  Native PXR runs use ordinary GC and disable the PHP worker executable.

The trivial print baseline measures about 2.3 ms for PXR and 28.3 ms for this
configured PHP CLI. Do not interpret the copy benchmark's PHP time, for example,
as 29.8 ms spent copying arrays: it includes that startup overhead. We do not
subtract separate startup medians to manufacture kernel-only timing. Running a
long-lived PHP server would have a different cost model. Compiler optimization
can simplify the integer loop heavily, so it is not a general loop-throughput
claim. No async, HTTP, database, PHP interop or parallel-worker workloads are
compared here; the async syntax is not accepted by ordinary PHP.

## What the slower cases suggest

These are implementation observations, not profiling measurements:

* Native array lookup currently linearly scans entries (`pxr_array_find` in
  `runtime/pxr_rt.c`); appending/indexing dense integer keys is a clear optimization
  target. The array workload appends 10,000 values and reads each index once.
* Source array assignments currently deep-copy value arrays (`pxr_array_copy`).
  The read-only copy workload copies a 1,000-element array 100,000 times and reads
  its first element. Improving value-array representation/copy behavior matters.
* `pxr_str_concat` allocates a new buffer and copies both operands. Repeated
  growing-string append therefore moves increasingly large amounts of data.
* The object workload constructs 2,000,000 two-property objects and calls an
  integer-returning method. Allocation, method and GC costs are included; this
  timing alone does not isolate which component causes the difference.

## Reproduce

```sh
cargo build --release -p pxr
python3 benchmarks/bench.py --repeat 9 --warmup 2 --opt 3 \
  --json /tmp/pxr-benchmark.json
```

See [raw samples and metadata](2026-10-16-m7.json), including source hashes,
outputs, all timings, PHP ini paths and compiler identity. Host load, OS executable
checks, PHP configuration and thermal state can change the results.
